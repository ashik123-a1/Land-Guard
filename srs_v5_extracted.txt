3. P3 verification and ownership engine
3.1 Ownership reconstruction
Replay parcel transaction/ownership events chronologically; show the recorded ownership sequence, event references and
gaps.
3.2 Double-selling
Detect conflicting sales for the same parcel or a further incompatible transfer after a recorded transfer; link both conflicting
events.
3.3 Seller–owner mismatch
Compare seller recorded on transaction with available ownership history; state exactly which references disagree.
3.4 Registration–mutation comparison
Compare available registration and mutation records; identify mismatched fields, dates, missing counterparts and source
references.
3.5 Rapid/suspicious transfers
Apply explicit versioned rules to unusually rapid sequences, duplicate references and defined suspicious patterns.
3.6 Forgery/alteration indicators
Use trusted-file hash comparison and/or verified CV/document checks. Explain that hash proves byte-level match to a trusted
baseline only; CV/ML signals are indicators, not proof.
3.7 Incomplete history
Identify missing records/time periods; return insufficient evidence rather than treating absence as proof of no conflict.
3.8 Ownership timeline
Visual timeline of synthetic parties, transfers, dates, source references and conflicts.
3.9 Transaction/ownership graph
Graph relationships between parcels, transaction events, parties/pseudonymous IDs and evidence.
3.10 Cross-parcel analysis (Phase 3)
Find repeated patterns across the synthetic dataset, state dataset scope and provide linked evidence.
Every finding MUST include finding code, severity, explanation, source record references, engine/rule version,
run timestamp and limitations. No score alone can establish legal ownership or prove fraud.

5. Complaint reporting and case management
 • Complaint form and optional voice entry; categories: suspected double sale, ownership conflict, document-integrity concern,
 record mismatch, other.
• Unique human-readable complaint/case reference for each accepted complaint; idempotency/duplicate-submission
 protection.
• Permitted evidence uploads/references with file validation, access control, metadata and hash.
 • AI complaint analysis: extract claims, parcel references, category and possible duplicate reports; all are suggestions until
 reviewed.
• Claim/evidence matching states: SUPPORTED_BY_AVAILABLE_RECORDS, CONTRADICTED_BY_AVAILABLE_RECORDS,
 UNVERIFIED; each state links evidence and reason.
• Controlled case states: SUBMITTED, UNDER_REVIEW, AWAITING_INFORMATION, ESCALATED, RESOLVED, CLOSED, REOPENED;
 enforce allowed transitions.
• Investigator notes, clarification requests, response attachments, finding and closure outcome; preserve full history rather
 than overwrite.
• Assignment/reassignment history with actor, timestamp and rationale.
 
6. Citizen progress, priority and expedited review
 • Personal dashboard shows only authenticated user's cases, statuses, timeline, last update and permitted report links.
 • Record submitted_at, first_review_at, last_updated_at, resolved_at, elapsed pending time and investigation duration.
 • Configurable review targets, overdue flags and escalation; targets are not promises of resolution.
 • Expedite request reasons: potentially imminent transaction, new evidence, excessive waiting time, other justified urgency.
 • Admin may approve, reject or request more information; store decision and reason.
 • Priority values Critical, High, Normal, Low. AI may recommend; authorized admin confirms/changes with justification.
 • Notify users about accepted complaint, relevant assignment/status updates, requests for information, expedite decision,
 closure and overdue events.
• Keep duplicate expedite-request protection and full request history.
 
7. Admin and investigator dashboard
 • Overview of total, pending, urgent, unassigned and overdue cases.
 • Search/filter/sort, category breakdowns, pagination and case-age/workload views.
 • Assignment/reassignment, manual priority and required justification.
 • Evidence review and transaction history comparison in a unified case workspace.
 • Expedited-review approval queue; request-for-information workflow.
 • AI-generated summaries and preliminary risk recommendations grounded in persisted records.
 • Controlled notifications, status updates, escalation, closure and reopening.
 • Audit trail for assignments, priority changes, decisions, rule changes and evidence access.
 • Backend-enforced role permissions for every protected operation; hiding a button is not authorization.
 
8. Verification reports, QR and document integrity
 • Report includes parcel reference, data sources, checks performed, extracted fields, conflicting references, finding rationale,
 limitations and next steps.
• Unique report ID and optional QR code leading to a controlled public summary.
 • Public report must exclude private complaint details and sensitive identity fields.
 • SHA-256 comparison detects whether uploaded bytes match a previously recorded trusted file hash; it does not establish
 authenticity by itself.
• Document-to-record comparison checks confirmed extracted/manual fields against available local permitted records.
 • OCR fields retain confidence/source and reviewer correction history; never silently overwrite user-entered values.
 • Document upload types, maximum size, MIME/content validation, scanning hook where available, storage key and hash are
 specified.
• Every generated synthetic document and report is visibly watermarked “SYNTHETIC DEMO — NOT AN OFFICIAL DOCUMENT”.

15. Security, privacy and data governance
 • Enforce authentication and role authorization server-side on every protected route and resource.
 • Prevent IDOR/cross-user access to complaint, case, evidence and report IDs.
 • Validate inputs; use parameterized queries; rate-limit login, lookup, upload and complaint endpoints.
 • Validate upload extension, MIME and actual content; enforce size limits; generate safe filenames; block path traversal.
 • Keep secrets server-side; TLS for network traffic; sanitize logs; avoid leaking sensitive data in error responses.
 • Store minimum necessary personal data; define retention and deletion for uploads, complaint data and derived OCR text.
 • Audit access and changes with actor, timestamp, action, object, reason and request ID; protect audit integrity.
 • Separate synthetic records from permitted public/authorized records with explicit provenance and flags.
 
• Admin changes do not alter government records; sensitive edits require review/change request.
 • Public QR/report only returns allow-listed fields and uses unguessable tokens; revocation/expiry should be supported if
 practical.
• AI-generated content is advisory; human review for case outcomes and priority; do not treat voice as identity.
